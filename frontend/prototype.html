Platform ⇄ Chatbot 状态桥接原型

演示「改了项目，对话里没跟上」是怎么被修掉的。左侧模拟 Platform，右侧模拟 Chatbot（真实环境里它是 iframe）。 两个面板跑的是同一份桥接层代码，通信走 postMessage + 同源校验，与生产一致。

Platform 原生 JS · 状态写入方
Platform 状态projectId=""
事件日志
Chatbot React · 状态订阅方（生产中是 iframe）
对话中的项目 未就绪 等待挂载
对话工作台 —
正在等待与 Platform 建立连接…
订阅回调日志

✓用这个原型验证三件事

1. 切项目立即同步。左侧换项目，右侧对话里的项目名立刻跟着变，不需要手动刷新。

2. 重复值不重复广播。反复选同一个项目，右侧日志不会重复打印 —— 去重只在 store 里做一次，各 hook 不用自己比对。

3. 迟到者能拿到当前值。点「重载对话窗口」，右侧会先显示未就绪，随后自动拿到当前项目。这正是原实现里最容易断的地方：Platform 在挂载时就广播，而 iframe 还没监听。

1原实现为什么会不同步

一条 agentflow-project-context 消息，在 Chatbot 侧被四个独立监听器分别处理：

useChat.js→ selectRef.current(id)
useLocalConversations.js→ selectLocal(null)
useExecutionMachines.js→ 监听 environments-changed
App.jsx→ 监听 mention-issue

每个 hook 还各自维护一份 ref 做去重：

useChatglobalProject.current
useLocalConversationshostProjectRef.current

问题：同一份状态有四个副本。任何一处没跟上、或执行顺序不对，界面就停在旧项目上。

2更隐蔽的是时序问题

Chatbot 的 iframe 初始是 src="about:blank"，加载完成后才真正挂载 React。

而 Platform 在切换项目时就广播了。此时 Chatbot 还没注册监听器，消息直接丢失。

现有代码的兜底是「收到 chat-ready 后再补发一次」，但补发逻辑分散在 app.js 的多个位置，容易漏。

在「交互演示」里点「重载对话窗口」，可以看到桥接层用另一种方式解决：订阅时立即读取当前值，而不是依赖补发。

1改前 vs 改后

改前 · 裸 postMessage
// 每个 hook 自己听
useEffect(() => {
  const onCtx = (e) => {
    if (e.origin !== origin ||
       e.source !== parent) return;
    if (e.data?.type !== "…-context") return;
    if (id === ref.current) return; // 各自去重
    ref.current = id;
    selectLocal(null);
  };
  addEventListener("message", onCtx);
}, []);
改后 · 桥接层
// 一处订阅，来源校验与去重都在层内
useEffect(() => {
  return bridge.subscribeProject(
    (projectId, previous) => {
      selectLocal(null);
    }
  ); // immediate 已内置
}, [bridge]);
来源校验、消息类型、去重都在桥接层里做一次。 hook 只关心「项目变了，我要做什么」。

2这一层不做什么

它不接管业务逻辑。切项目时该清空草稿、该重新拉会话、该保留哪些缓存，仍由各 hook 自己决定。

它只回答一个问题的唯一答案：当前项目是哪个。
