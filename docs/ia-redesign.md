# AgentLoop 信息架构（IA）重构设计

> 状态：设计稿，待评审
> 范围：前端导航、视图组织、任务主视图、角色会话
> 后端改动：**零**（本方案完全复用现有 API）

---

## 1. 背景与问题

### 1.1 现状诊断

当前平台的导航按**技术模块**划分，而非按**用户工作流**划分。这导致四个具体症状：

| # | 症状 | 代码证据 |
| --- | --- | --- |
| 1 | 首页"任务运行"埋在会话列表下、默认折叠、无新建入口 | `web/index.html:137` `collaboration-tasks` 位于 `sidebar-conversations` 内 |
| 2 | 一级导航无"任务"，任务无独立详情页 | rail 仅 5 项：`collaboration/observability/issues/approvals/settings` |
| 3 | 角色只能借 `@` 临时调用，无法建立独立会话 | `internal/httpapi/assistant_subagents.go` 已支持 `role-<name>` subagent，前端无入口 |
| 4 | 流程模板、运行记录、定时任务全埋在"设置"二级导航 | `web/index.html:148-150` |

### 1.2 根因

现有二级导航的顺序直接映射了 `internal/httpapi/` 的 handler 分组：

```
个人配置 | AI助手 | 项目配置 | 通道管理      ← 配置类 handler
流程模板 | 运行记录 | 定时任务               ← 执行类 handler
角色定义 | 能力资产 | 执行机器 | 环境资产     ← 资产类 handler
```

而用户在头脑中的分类是：

```
"我要干活"  → 任务、需求、审批
"我要协作"  → 会话、角色
"我要调教"  → 流程、角色、技能
"我要排障"  → 运行、日志
"我要管理"  → 项目、成员、机器、密钥
```

### 1.3 设计原则

1. **数据流优先于模块**：按 `需求 → 任务 → 运行` 的真实链路组织
2. **高频上浮**：任务、审批、会话放一级；配置下沉
3. **单一真相**：同一实体只有一个主视图，其他位置只做引用
4. **零后端改动**：所有改造只重排前端，复用 `/api/tasks`、`/api/runs`、`/api/assistant/*`

## 2. 数据模型回顾（理解 IA 的前提）

```
project (项目)
   └── issue (需求)  1:1..n
          └── task (任务)  1:n          ← 调度实体：DispatchMode = primary/scheduled/rerun
                 └── run (运行)  1:1    ← 执行实体：节点/产物/审批/日志
```

`task` 是唯一携带**调度语义**的实体（`internal/domain/task.go`）：

```go
type Task struct {
    ID           string  // 任务 ID
    IssueID      string  // 来源需求
    AgentID      string  // 执行角色
    WorkflowID   string  // 使用的 SOP
    RunID        string  // 产生的运行
    Status       string  // queued|dispatched|running|completed|failed|cancelled
    DispatchMode string  // primary|scheduled|rerun
    TriggerOrigin string // manual|timer|manual_run
}
```

**关键结论**：
- 任务是"干活"的最小单位，必须是一级概念
- 运行是任务的实现细节，**并入任务视图**（不单独做导航）
- 一次任务 = 一次运行，`rerun` 会产生新 task

### 4.2 任务详情（合并"运行记录"）

**目标**：一个任务 = 一条垂直时间线，包含所有阶段、产物、审批、日志。

```
┌─ 任务详情 ──────────────────────────────────────────────────┐
│ ← 工作台   需求「登录页改造」  ›  通用后端 SOP               │
│                                                             │
│ 状态：运行中   角色：开发实现   耗时：12分    Token：8.2k    │
│ [暂停] [取消]  [打开需求]  [查看源码]                        │
├─────────────────────────────────────────────────────────────┤
│ 阶段进度                                                    │
│ ①需求定型 ✓ → ②方案设计 ✓ → ③开发实现 ● → ④评审 ○ → ⑤验收 ○│
├─────────────────────────────────────────────────────────────┤
│                                                             │
│ ✓ 需求定型                        CodeBuddy · 2分 · 1.2k    │
│   └ requirement.md          [预览] [下载] [版本 1]          │
│                                                             │
│ ✓ 方案设计                        CodeBuddy · 3分 · 2.4k    │
│   └ design.md               [预览] [下载] [版本 1]          │
│                                                             │
│ ● 开发实现                        CodeBuddy · 运行中         │
│   ├ 当前：正在修改 src/auth/login.tsx                       │
│   ├ 工具调用 23 次               [展开实时轨迹 ▾]           │
│   └ 日志                         [展开 Worker 日志 ▾]       │
│                                                             │
│ ⏸ 人工验收                        ← 未到达                   │
│                                                             │
│ ○ 独立评审 / 测试验证 / 交付汇总                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**关键设计**：
- **垂直时间线**，每个节点是一个可折叠卡片
- 节点完成 → 产物**内联**在卡片内（`[预览] [下载] [版本 n]`）
- 运行中节点 → 展开实时轨迹/日志（**默认折叠**，避免干扰）
- **审批内联**：到达人工关口时，卡片内直接出现"批准/退回"按钮，不跳转
- 底部提供"从这里重跑"（复用 `data-rerun-from-here`）

**复用现有能力**：
- 节点拓扑 → 改为垂直列表（数据结构不变）
- `runs.js` 的 `nodeInspector`、`nodeArtifacts`、`telemetryItemHTML` 全部可复用
- 审批 → `approvals.js` 的 `approveRun/rejectRun`

**多次运行**：
```
任务 1（primary）  ✓ 完成 2026-11-20 14:00  [展开]
任务 2（rerun）    ● 运行中 2026-11-21 10:00  [展开]  ← 默认展开最新的
```
列表按时间倒序，最新展开。

## 5. 关键用户旅程

### 5.1 正常交付（主路径）

```
工作台
 └ [＋ 新建需求] → 填写 → 选择 SOP → 启动
     └ 自动跳转「任务详情」，实时看时间线
         └ 到达人工验收 → 卡片内直接 [批准]
             └ 继续执行 → 交付完成
                 └ 通知：MR !128 已创建
```

**点击次数**：新建需求(1) → 批准(1) = **2 次关键操作**

对比现状：新建(1) → 等 → 去"待我确认"(1) → 批准(1) → 去"需求列表"(1) → 找需求(1) → 切 tab(1) = **6 次**

### 5.2 和角色聊需求

```
角色 → 点「需求定型」的 [发起会话]
     └ 跳转协作，会话已绑定该角色
         └ 输入需求描述 → 角色输出 requirement.md
             └ 可转为需求：对话内 [创建需求] 按钮
```

### 5.3 排障

```
工作台 → 点失败任务卡片
     └ 任务详情，失败节点自动展开
         └ 看日志/轨迹 → [从这里重跑]
```
